# 10 Task actions v2

Selected task-actions-v2.png generated with built-in imagegen; exact prompt in prompt.json. This design precedes implementation. App sources and harness remain frozen.

## Existing protocol, verified from source
- controllers/action.go and models/action.go: Task fields task_id, member_id, content, due_date (YYYY-MM-DD), done, parent_id, topic_id, child counts, create/modify/complete times. GET /api/tasks/:id; POST /api/tasks; PUT /api/tasks/:id; PATCH /api/tasks/:id/done. No batch creation/creation-key receipt protocol on ordinary task POST.
- actionTaskRequest accepts content, due_date, done, parent_id, optional topic_id. PUT omitting topic_id preserves old topic; explicit 0 clears it. Omitting parent_id or done resets them to 0/false; empty due_date becomes seven days from server today. Content is trimmed and limited to 1000 runes.
- GetTask and task parent/topic checks use checkOwnership, which permits administrator access. UI must bind actual member ID and not infer own-write authority merely from a successful read. Current TaskItem drops member_id; the actions adapter needs an owned raw snapshot or a new explicitly owned read boundary.
- controllers/topic.go: GET /api/topics?page=&keyword= yields member-filtered real topics. TopicItem has topic_id/title/member_id and other summary fields. GET /api/topics/:id fresh-validates a selected ID; use current user's topics only. Existing TopicsRepository read/list can supply remote choices; no local topic repository exists. Local UI must hide unavailable topic action and preserve unknown existing topic IDs.
- static/js/tasks.js openTaskAI calls notesApp._openInlineAIPrompt with scene task, parent content context, text-only instructions, and four defaults: organize task, split to 3-7 checklist items, smallest action for today, 2-5 acceptance criteria.
- static/js/notes.js _runInlineAI -> static/js/ai-helper.js AIHelper.complete -> POST /api/ai/complete with messages/scene/temperature/max_tokens. SSE is OpenAI delta content plus DONE. This edits composer text only; it does NOT create children or invoke task SQL. Existing 06 propose_task means a NEW proposal, not existing-task update.

## Four screens and explicit boundaries
1. Fresh owned current-task read-only view shows complete content and exact due/parent/topic/done context. Enter AI suggestion with the actual edited snapshot, not stale list preview. Existing data cannot disappear while AI runs.
2. AI output is a separate read-only proposal. Stop/interrupted stream never writes partial output into the editor automatically. Explicit Put into editor replaces only content in the same-ID editor; user edits and saves through existing owner coordinator. Parent, due date, done and topic stay exact. Immediately before applying, compare the originating full editor fingerprint; changed text/context requires another preview, never silent overwrite. Model has no SQL/save tools.
3. Split output stays Markdown checklist suggestions. No invented batch API, model INSERT or automatic multi-create. A user can explicitly choose one suggestion to open one new child editor with parent=current task ID, done=false, inherited date/topic visible for review. Only the editor's explicit Save creates it. Ordinary task POST has unknown-response duplication risk: do not enable this create action until a durable per-child create journal/receipt-safe path exists. Until then offer Copy suggestion/manual navigation, labelled honestly. Completed child IDs require explicit durable row status before another suggestion can create; no automatic replay after uncertain result.
4. Topic picker uses real owned paged topics, search and load more. Cancel leaves all editor fields unchanged. Stage a selection, then Use selected topic; fresh detail/member check before returning positive ID. No topic returns explicit 0, preserve current returns null result (different semantics). Unknown/deleted current topic displayed by ID and retained unless user explicitly clears. Never pick topic by matching its title.

## Component plan
External scratch only: typed TaskActionSnapshot plus pending suggestion (origin full fingerprint); pure apply-to-draft helper preserves every TaskItem identity/parent/date/done/topic/complete-time/count; typed TopicChoice distinguishes cancel/clear/set. Small read-only preview and topic picker callbacks return draft changes only, never repository writes. A read-only suggestions backend may reuse actual scene=task SSE. Local model can supply text-only suggestions with no tools, not 06 draft creator or direct SQL.

## Acceptance before product integration
Verify rewrite/cancel/stop/scope retirement; fresh origin changed guard; exact preservation parent/date/done/topic and same ID; real owned topic pages/search/fresh read; cancel vs explicit clear 0; deleted/foreign topic; partial/unknown subtask POST blocking; child never auto-created; content Unicode/1000rune bound; EN320/200% font/keyboard; source-level and real ARM64 redroid tests after shared build stage. Prototype is not Native acceptance evidence.

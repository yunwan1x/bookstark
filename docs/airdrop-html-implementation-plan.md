# Airdrop HTML 实施文档

本文档用于暂存分享页“airdrop文件分享助手”单文件工具的待实施需求。

## 使用规则

- 用户提出该工具相关的新增、修改、删除、重构、交互调整或代码整理需求时，先整理到本文档，不直接修改实现代码。
- 每次更新本文档后，在回复中说明本次新增、修改或删除了哪些实施项。
- 只有用户明确说“实施”或“按文档实施”时，才根据本文档集中修改 `tmp/share-1783432865442847645.html` 及相关测试和文档。
- 实施完成并通过必要回归后，将对应实施项从 `[ ]` 改为 `[x]`；不要清空本文档，除非用户明确要求清空。
- 未明确要求部署、发布或更新线上时，不执行线上发布流程。

## 待实施项

### 1. [x] 音视频分享改为页面内嵌控制，并支持同时分享给多台设备

目标：

- 摄像头和麦克风不再通过 modal/sheet 弹窗控制，避免控制状态脱离房间主界面。
- 保留一次采集本地 `MediaStream`、分别通过各设备的 `RTCPeerConnection` 发送的现有 P2P 架构。
- 同一个摄像头和麦克风流可以同时发送给多台已连接设备。

交互设计：

- 在“设备”页发送区上方增加内嵌音视频控制区。
- 未开始分享时保持紧凑，显示目标设备选择和“开启音视频”入口。
- 分享后展开本地预览、当前接收设备数量、摄像头开关、麦克风开关和停止分享操作。
- 分享状态区显示实际接收设备名称和逐设备状态：`协商中`、`直播中`、`发送失败`；设备较多时默认显示前两台和 `+N`，可展开完整列表。
- 每台正在接收的设备提供独立取消入口；控制区同时提供明确的 `停止全部分享` 操作。
- 切换“设备/直播”页签时，媒体流和控制状态保持，不重复申请浏览器权限。
- 小屏下使用全宽两行布局，不覆盖设备列表、文本输入和系统键盘区域。
- 权限申请、设备缺失、轨道结束、协商失败和部分设备发送失败均显示明确状态，不能只关闭控制区。

多设备规则：

- 分享前必须明确选择一个或多个已建立点对点连接的目标设备；未选择设备时不能开始分享。
- 支持多选设备，同一个本地 `MediaStream` 分别添加到每个已选择设备的 `RTCPeerConnection`。
- 不默认广播给全部设备，也不因房间当前只有一台设备而跳过目标确认。
- 分享期间新连接的设备只进入可选列表，默认不接收当前音视频流。
- 分享期间修改目标选择时，新选设备独立添加 sender 并完成媒体协商；取消选择的设备只移除自身 sender，不影响其他接收设备和本地采集流。
- 取消单台设备时只移除该 PeerConnection 的音视频 sender 并完成必要协商，其他已选设备继续接收。
- 取消最后一台接收设备时显示 `停止音视频分享？` 确认；确认后按停止全部处理，关闭并释放本地摄像头和麦克风轨道。
- 切换目标时允许先选择新设备，再取消旧设备；只要仍有接收设备，本地采集流保持，不重复申请权限。
- `停止全部分享` 会先通知全部接收设备，再移除所有媒体 sender、完成必要协商并释放本地媒体轨道。
- 发送失败的设备在列表中保留失败状态，并提供 `重试` 和 `移除`；重试只重新协商该设备。
- 某台设备离开或协商失败时，只清理该设备的 sender，不中断其他设备和本地采集流。
- 摄像头、麦克风开关状态同步给所有接收设备。
- 停止分享时移除各 PeerConnection 中对应的 sender、完成必要协商并释放本地媒体轨道。
- UI 明确提示 P2P 多设备分享会随接收设备数量增加上传带宽和浏览器负载。

QA：

- 单接收端开启、关闭、重新开启摄像头和麦克风正常。
- 选择两个及以上接收端后，它们同时获得持续音视频，关闭其中一端不影响其他设备。
- 未选择的在线设备不能收到音视频。
- 分享期间新设备加入后默认不接收；手动勾选后才能开始接收。
- 摄像头关闭但麦克风开启、麦克风静音但摄像头开启均能正确工作。
- 拒绝权限、没有媒体设备、单个 Peer 协商失败时状态和恢复入口正确。
- 切换页签、大小屏变化及页面滚动不会中断媒体流或遮挡控制。
- 回归文件发送、文字发送、设备选择、直播单路/宫格和离开房间流程。

### 2. [x] 文件、文字和音视频统一使用多选目标设备

目标：

- 文件、文字和音视频共用一套目标设备选择状态和交互，不再存在“文件单选、文字自动发送、音视频多选”等不一致行为。
- 所有发送动作都必须由用户明确选择接收设备，避免误发。

交互设计：

- 附近设备列表支持多选，使用明确的 checkbox/选中标记，不再使用只能表达单选的选中态。
- 发送区持续显示 `已选择 N 台设备`；可以点击该状态定位或展开目标设备列表。
- 未选择设备时，文件、文字和音视频发送入口均禁用，并显示 `请选择接收设备`。
- 即使房间里只有一台设备，也不自动选中、不自动发送。
- 新加入设备默认不选中；离开设备自动从选择集合移除。
- 点击已选设备可以取消选择；提供紧凑的 `全选` 和 `清空` 操作，但全选不会成为默认状态。
- 切换设备/直播页签不清空选择；离开房间或切换房间时清空全部选择。

发送规则：

- 使用稳定的 `selectedTargetPeerIds` 集合保存选择，不再只保存单个 `selectedTargetPeerId`。
- 每次开始发送时对当前目标集合生成快照，发送过程中后续选择变化不改变该次文件或文字任务的接收范围。
- 文字消息将同一 payload 分别发送给每个已选设备，并记录成功、失败和部分成功状态。
- 文件传输为每个接收设备建立独立任务、进度和失败状态；一台设备失败不能取消其他设备的传输。
- 音视频分享目标可以在分享期间增减：新增目标执行独立媒体协商，取消目标仅移除该设备的媒体 sender。
- 往来记录需要显示目标设备或目标数量，并能查看每台设备的结果。

QA：

- 一台设备在线但未选择时，文件、文字和音视频入口均不可发送。
- 单选设备时，只有该设备收到对应内容。
- 多选两台以上设备时，所有已选设备收到文字、文件或音视频，未选设备不接收。
- 多设备文件传输显示独立进度；一个接收端离开后，其他接收端继续完成。
- 发送开始后修改选择，不改变已经开始的文件或文字任务目标。
- 分享音视频期间增减选择，只影响对应设备。
- 逐设备状态能正确区分协商中、直播中和发送失败，并显示实际设备名称。
- 取消一台接收设备后，其他设备持续播放；取消最后一台时必须确认，确认后浏览器媒体轨道结束。
- 先增加新设备再取消旧设备时，本地预览和采集轨道不中断。
- 停止全部分享后所有接收端停止播放，本地摄像头和麦克风权限被释放。
- 单设备协商失败后可以只重试或移除该设备，不影响其他设备。
- 新设备加入默认不选中；设备离开、房间关闭和切换房间后的选择状态正确清理。

### 4. [x] 增加逐设备 WebRTC 连接与音视频诊断面板

目标：

- 帮助用户判断摄像头画面持续延迟、卡顿或质量下降来自网络、编码、接收缓冲还是设备性能。
- 诊断数据按设备独立采集，不能把多台接收设备的数据混为一个全局状态。
- 不把 RTT 或 jitter buffer 单独标成“端到端延迟”；UI 明确区分网络往返、接收缓冲和解码处理。

信息架构：

- 一级摘要常驻设备卡：
  - 状态圆点与 `良好`、`一般`、`拥塞` 或 `无媒体`。
  - 音视频分享时补充紧凑摘要，例如 `24 FPS · 1.6 Mbps · RTT 18 ms`。
  - 无音视频时只显示 DataChannel/PeerConnection 连接状态，不显示无意义的 `0 FPS`。
- “附近设备”标题区的 `测试连接` 调整为 `连接诊断` 入口，并显示当前最差设备状态，例如 `连接诊断 · 1 台拥塞`。
- 点击入口打开非阻塞诊断面板：
  - 大屏在“附近设备”区域右侧展开约 `360px` 的内嵌侧栏，主发送区仍可操作。
  - 小屏在设备区下方展开全宽 accordion，不使用遮挡页面的 modal。
  - 面板可收起；收起后保留设备卡摘要。
- 多设备场景在面板顶部使用设备下拉菜单或纵向设备列表切换，默认定位到质量最差的设备。

诊断面板内容：

- 总览：质量等级、采样时间、当前是否正在向该设备发送媒体。
- 链路：候选类型 `局域网直连 / 公网直连 / 中继`、协议、RTT、可用出站码率。
- 视频发送：实际编码分辨率、FPS、发送码率、累计编码帧、丢弃帧、关键帧、质量受限原因。
- 视频接收：实际解码分辨率、FPS、接收码率、丢包率、jitter、平均接收缓冲、平均解码耗时、丢帧。
- 音频：发送/接收码率、丢包率、jitter、平均缓冲和音频能量；没有音频轨道时整组隐藏。
- 建议区：按指标显示具体建议，例如 `接收缓冲持续偏高，建议切换 720p/24fps`、`发送端编码受 CPU 限制` 或 `当前为局域网直连，网络 RTT 正常`。
- 操作：`重新采样`、`复制诊断信息`；第一版不自动修改分辨率、不自动重连，避免诊断动作改变现场状态。

采集与计算：

- 媒体分享期间每 `1s` 调用对应 PeerConnection 的 `getStats()`；没有媒体时降为每 `3s` 或停止媒体指标采集。
- 面板关闭时只保留设备卡摘要所需的低频采样，避免多设备场景持续高频遍历统计对象。
- 使用相邻两次字节数、帧数和时间戳差值计算码率与 FPS，不直接展示累计值充当实时值。
- 平均接收缓冲使用 `jitterBufferDelay / jitterBufferEmittedCount` 的增量计算。
- 平均解码耗时优先使用 `totalDecodeTime / framesDecoded` 的增量计算；字段缺失时显示 `--`。
- 候选链路从 selected candidate pair 及 local/remote candidate 获取；无法确认时显示 `未知`，不能推测为直连。
- 质量等级基于连续多个采样窗口，至少连续 `3s` 越过阈值才降级，避免状态圆点每秒抖动。
- 指标值使用固定宽度或 tabular numbers，刷新时布局不能左右跳动。

首版参考阈值：

- `良好`：RTT `< 100ms`、丢包 `< 1%`、平均接收缓冲 `< 120ms`，且实际 FPS 不低于目标的 80%。
- `一般`：RTT `100–200ms`、丢包 `1–3%`、平均接收缓冲 `120–300ms`，或 FPS 低于目标的 60–80%。
- `拥塞`：RTT `> 200ms`、丢包 `> 3%`、平均接收缓冲 `> 300ms`，或 FPS 持续低于目标的 60%。
- 浏览器不提供某项指标时不参与评级，不能把缺失值当作 0。

QA：

- 单接收端和三个接收端时，每台设备数据独立且不会串值。
- 开始/停止摄像头、切换麦克风和增减接收设备后，指标分组随轨道状态正确出现或隐藏。
- 码率、FPS、缓冲和解码耗时使用增量计算，空字段显示 `--`，无 `NaN`、`Infinity`。
- selected candidate pair 能正确区分局域网直连、公网直连和 relay；无法确定时显示未知。
- 状态等级有防抖，数据刷新时设备卡和面板布局稳定。
- 复制诊断信息不包含房间凭据、SDP、IP 地址或 ICE candidate 原文。
- 大屏内嵌侧栏和小屏 accordion 不遮挡设备选择、文件/文字发送及音视频控制。
- 面板持续打开 10 分钟不产生计时器叠加、明显 CPU 增长或已关闭 PeerConnection 的采样异常。
